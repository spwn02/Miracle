# Feature engine

Miracle's Feature engine is the compile-time configuration substrate used by optional facilities, ecosystem extensions, capability-sensitive APIs, and future modules such as UUID, Serde, and Clap.

The engine deliberately separates two questions that ordinary C++ feature macros tend to conflate:

```text
What implementation was compiled into this Miracle build?
                          |
                          v
                 BuildFeatureSet

What behavior does this particular compile-time consumer select?
                          |
                          v
                    FeatureSet
```

The build system is responsible only for the first question. Once configuration crosses into C++, feature reasoning is expressed through structural C++ values, concepts, constant evaluation, and generated module configuration. Preprocessor state is not the public feature API.

## Design invariants

The Feature engine follows these hard rules:

- feature descriptors are structural compile-time values;
- feature identity is the stable feature name, not a C++ type identity;
- build features and semantic features are distinct;
- required dependencies and implications resolve transitively;
- optional dependencies are metadata and never silently enable their target;
- resolution is deterministic and canonicalized in catalog order;
- dependency and implication cycles are rejected;
- conflicts are checked after complete transitive closure;
- build features cannot be selected if their implementation was not compiled;
- capability requirements are checked during resolution;
- groups are selectors and never become hidden runtime state;
- disabled heavy implementation does not enter the target source set;
- the configured build universe contributes to module/build identity;
- third-party descriptors and descriptor metadata are first-class;
- invalid feature configurations are diagnosed at compile time rather than becoming runtime branches.

The engine is a bootstrap facility. It intentionally does **not** depend on the later Structural Trait engine. Once Traits exist, Feature descriptors can also participate in that ecosystem without introducing a dependency cycle.

## Modules

The implementation consists of two public module partitions:

```cpp
import Miracle:Feature;
import Miracle:FeatureConfiguration;
```

Normal users simply write:

```cpp
import Miracle;
```

`Miracle:Feature` contains the generic structural engine. It can be used by third-party libraries without depending on Miracle's configured global state.

`Miracle:FeatureConfiguration` is generated by the build. It exposes the actual build universe and capability universe selected for the current Miracle configuration.

## Defining a feature

`feature::define` constructs an empty structural descriptor value:

```cpp
inline constexpr auto logging = feature::define<"logging">(
    feature::semantic,
    feature::description<"Structured logging support">,
    feature::version<1, 0, 0>,
    feature::defaultEnabled);
```

The feature object contains no dynamic state. All descriptor metadata is encoded in its type, which keeps feature values suitable for non-type template parameters and allows compile-time consumers to inspect the metadata without allocation.

### `Descriptor<Name, Options...>`

`Descriptor` is the concrete type produced by `define`.

Its public static metadata is:

```cpp
Descriptor::name
Descriptor::description
Descriptor::version
Descriptor::featureKind
Descriptor::enabledByDefault
```

and its public metadata queries are:

```cpp
Descriptor::dependencies()
Descriptor::optionalDependencies()
Descriptor::conflicts()
Descriptor::implications()
Descriptor::capabilities()
Descriptor::groups()
Descriptor::forEachOption(function)
```

`forEachOption` intentionally includes unknown custom options. This is how third-party tooling can attach metadata without requiring Miracle to understand or enumerate every future ecosystem concern.

A descriptor may contain at most one description, one version, one explicit feature-kind option, and one `defaultEnabled` marker. Violating those singular metadata rules is a compile-time error.

## Descriptor option vocabulary

### Description

```cpp
feature::description<"Human-facing description">
```

The description is represented by `BasicStaticString` and requires no dynamic allocation.

### Version

```cpp
feature::version<2, 1, 4>
```

The value is exposed as:

```cpp
feature::Version{
    .major = 2,
    .minor = 1,
    .patch = 4,
}
```

A feature's version is metadata. The feature's stable name remains its identity. Versioned families may still use separate names where the version genuinely selects different functionality, for example a future `uuid.v7` feature.

### Feature kind

```cpp
feature::build
feature::semantic
```

A descriptor is semantic when neither marker is supplied.

A **build feature** selects compiled implementation. It may only resolve when its stable name belongs to the configured `BuildFeatureSet`.

A **semantic feature** selects compile-time policy that requires no missing heavy implementation and may therefore be enabled locally.

The distinction prevents a local template argument from pretending that an uncompiled module or dependency exists.

### Default state

```cpp
feature::defaultEnabled
```

`Catalog::analyzeDefaults` / `resolveDefaults` use this metadata as their seed. Default selection still goes through normal dependency, build-universe, capability, and conflict validation.

## Relationships

### Required dependency

When the target descriptor already exists:

```cpp
inline constexpr auto base = feature::define<"base">();
inline constexpr auto child =
    feature::define<"child">(feature::dependsOn<base>);
```

When forward declaration by descriptor value would make the graph impossible to express, use the named form:

```cpp
inline constexpr auto first =
    feature::define<"first">(feature::dependsOnNamed<"second">);
```

Named relationships are particularly important for cycle diagnostics. A feature model that required every target object to be declared first would make actual dependency cycles unrepresentable rather than diagnosing them.

Required dependencies are enabled transitively.

### Optional dependency

```cpp
feature::optionallyDependsOn<other>
feature::optionallyDependsOnNamed<"other">
```

Optional dependencies are descriptive metadata only. They never silently enable the target. Future facilities may inspect the relation to provide enhanced behavior when both features are already enabled.

### Implication

```cpp
feature::implies<other>
feature::impliesNamed<"other">
```

Implications participate in the same transitive closure as dependencies. They express feature composition rather than an implementation prerequisite.

A future versioned family can therefore express, for example:

```text
uuid.v7 -> implies uuid
```

### Conflict

```cpp
feature::conflictsWith<other>
feature::conflictsWithNamed<"other">
```

Conflicts are checked **after** dependency and implication closure. As a result, request order cannot make an invalid configuration appear valid.

## Capability requirements

A feature can depend on capabilities discovered by Miracle's executable build probes:

```cpp
inline constexpr auto reflected = feature::define<"reflected">(
    feature::requiresCapability<feature::Capability::ReflectionCore>);
```

The current capability vocabulary is:

```text
ImportStd
ReflectionCore
ReflectionQueries
ReflectionAnnotations
ReflectionStaticStorage
ExpansionStatements
StdVocabulary
StdHive
```

`feature::CapabilitySet` stores the capability universe as a structural bit set. It provides:

```cpp
set.contains(capability)
set.with(capability)
set.without(capability)
```

`feature::detectedCapabilities()` adapts the generated `Miracle::capability::*` build facts into this generic set. This means capability probing happens once at the build boundary; feature resolution does not rerun or reconstruct compiler probes.

`feature::capabilityName(capability)` returns the stable build-facing spelling (`reflection_core`, `std_hive`, and so on) used by compile-time diagnostics. Diagnostics never expose enum ordinals as capability identities.

## Feature groups

`feature::Group` groups selectors without creating another feature:

```cpp
inline constexpr auto everything =
    feature::group<"everything", logging, tracing, metrics>;
```

A group can be requested anywhere an explicit feature selector can be requested:

```cpp
constexpr auto result = catalog.analyze<everything>(buildUniverse);
```

The group expands to its members, and each member then participates normally in transitive resolution.

Descriptors may also declare membership directly:

```cpp
inline constexpr auto logging =
    feature::define<"logging">(feature::inGroup<"defaults">);
inline constexpr auto defaults = feature::group<"defaults">;
```

When `defaults` is selected, catalog resolution expands both the group's explicit member pack and every descriptor whose `groups()` metadata contains `"defaults"`. This makes group/feature declaration order irrelevant and keeps C++ semantics in lockstep with the CMake bridge, which combines explicit `MEMBERS` and feature-side `GROUPS` in the same way.

## Catalogs

A catalog defines the complete descriptor universe for one resolution domain:

```cpp
inline constexpr auto features =
    feature::catalog<base, logging, tracing, metrics>;
```

Catalog order is canonical order. Resolution does not recreate types or sort the resolved set after every request; it enables bits corresponding to the catalog's stable descriptor positions.

This has two important consequences:

1. request order cannot alter result identity;
2. compiler work scales with one known catalog universe rather than repeated type-level set reconstruction.

### Catalog metadata

The catalog exposes:

```cpp
Catalog::featureCount
Catalog::messageCapacity
Catalog::npos
Catalog::size()
Catalog::forEach(function)
Catalog::findIndex(name)
Catalog::nameAt(index)
```

`messageCapacity` is computed from the complete catalog name set. Cycle and conflict diagnostics therefore have bounded structural storage without an arbitrary short-name assumption.

Duplicate stable feature names are invalid even when their C++ descriptor types are different.

## Non-terminating analysis

Use `analyze` when code needs to inspect invalid configuration as data:

```cpp
constexpr auto report =
    features.analyze<tracing, metrics>(feature::buildSet<>);

static_assert(report.succeeded());
static_assert(report.features.contains(tracing));
```

The result is `feature::ResolutionReport`:

```cpp
report.features
report.error
report.message
report.succeeded()
```

`ResolutionError` distinguishes:

```text
None
DuplicateFeature
MissingFeature
MissingBuildFeature
MissingCapability
DependencyCycle
Conflict
```

This non-terminating form is valuable for white-box tests and for higher-level validation facilities that want to compose the result into another diagnostic.

### Dependency cycles

Cycles include the complete discovered cycle path:

```text
feature dependency cycle: a -> b -> c -> a
```

Both dependencies and implications participate in cycle detection.

### Missing references

A required dependency or implication absent from the catalog is a `MissingFeature` error. Optional dependencies may be absent.

## Hard resolution

When invalid configuration should make the program ill-formed, use `resolve`:

```cpp
constexpr auto enabled =
    features.resolve<feature::buildSet<"gpu">, gpu>();
```

On failure, C++26 user-generated `static_assert` messages emit the structured `StaticString` resolution message directly.

Variants are available for explicit capabilities and defaults:

```cpp
Catalog::resolve<BuildFeatures, Requested...>()
Catalog::resolveWithCapabilities<BuildFeatures, Capabilities, Requested...>()
Catalog::resolveDefaults<BuildFeatures>()
Catalog::resolveDefaultsWithCapabilities<BuildFeatures, Capabilities>()
```

The build and capability universes are NTTP values in hard-resolution APIs so that the complete report remains a constant expression usable as a generated `static_assert` message.

## `FeatureSet`

A resolved local set is represented by:

```cpp
feature::FeatureSet<CatalogType>
```

Its public operations are:

```cpp
set.size()
set.empty()
set.contains("name")
set.contains(feature)
set.contains<feature>()
set.subsetOf(other)
set.fingerprint()
```

`FeatureSet` is structural and therefore usable as an NTTP.

Its enable-bit representation is public because C++ structural class-type NTTPs require public structural state. Direct mutation of that representation bypasses resolver invariants and is not the normal construction path, in the same sense that direct mutation of `BasicStaticString::storage/length` can violate the static-string invariant. Normal code obtains sets from a catalog resolver.

The resolver enforces the build boundary for every selected build-kind feature. Semantic features do not require compiled heavy implementation and may be added inside the available C++ catalog universe.

## `BuildFeatureSet`

A build universe is a structural set of stable build feature names:

```cpp
inline constexpr auto buildUniverse =
    feature::buildSet<"gpu", "network.tls">;
```

The public API is:

```cpp
BuildFeatureSet::size()
BuildFeatureSet::contains(name)
BuildFeatureSet::contains(feature)
BuildFeatureSet::fingerprint()
```

Duplicate names are rejected at compile time.

The fingerprint sorts names before hashing, so two equivalent sets produce the same deterministic fingerprint independent of declaration/request order.

## Global configured build state

The generated `Miracle:FeatureConfiguration` partition exposes:

```cpp
feature::buildFeatures
feature::buildCapabilities
feature::buildIdentity
feature::buildEnabled<Feature>
feature::current<Requested...>(catalog)
feature::defaults(catalog)
```

### `buildFeatures`

`buildFeatures` is the maximum heavy implementation universe compiled into this
Miracle build.

For now it intentionally does not retrofit legacy Miracle modules into optional features. Existing facilities remain required until their contracted dedicated redesign/revisit phase. New optional facilities can register themselves with the Feature engine immediately.

### `buildCapabilities`

`buildCapabilities` is the typed capability universe generated from executable probes.

### `buildIdentity`

`buildIdentity` is a SHA-256 text identity computed by CMake from:

- the canonical sorted build feature list;
- all currently probed capability results.

As a result, generated module configuration changes when the feature/capability universe changes. Incompatible configured BMIs are not silently treated as the same source configuration.

### `current`

```cpp
constexpr auto active = feature::current<tracing>(features);
```

This resolves against the actual generated build and capability universes.

### `defaults`

```cpp
constexpr auto active = feature::defaults(features);
```

This resolves all default-enabled catalog entries under the same generated constraints.

## Requirement annotations

Feature requirements can be attached to reflected declarations using a structural payload:

```cpp
[[= feature::require(logging, tracing) ]]
auto render() -> void;
```

`feature::Requirement` retains the feature descriptor values themselves, not only strings, and remains structural/NTTP-friendly without relying on `std::tuple` (which is not guaranteed to be structural).

It provides:

```cpp
Requirement::featureCount
requirement.features
requirement.contains(name)
```

### Why the spelling is `require`, not `requires`

The design discussion used the aspirational spelling:

```cpp
[[= requires(feature) ]]
```

`requires` is a C++ keyword and therefore cannot be the name of an annotation factory/function in standard C++26. Miracle does not use lexical/preprocessor hacks to manufacture non-standard syntax. The standard-accurate spelling is:

```cpp
[[= feature::require(feature) ]]
```

The semantics are otherwise identical to the locked requirement-annotation model.

## Disabled-feature façade diagnostics

Heavy implementation can disappear while a lightweight public façade remains. Such a façade can call:

```cpp
feature::requireEnabled<requiredFeature, currentSet>();
```

When the feature is disabled, compilation fails with a generated message such as:

```text
feature `uuid.v4` is not enabled

help:
  enable `uuid.v4` in the active Miracle FeatureSet
```

The helper itself requires no heavy implementation partition. Future Diagnostics engine can later render the same semantic failure through the common diagnostic vocabulary without changing feature-selection semantics.

## Third-party descriptors

Miracle does not require feature values to be produced by `feature::define`. Any type satisfying the bootstrap `feature::Feature` concept can participate:

```cpp
struct MyFeature final {
  static constexpr auto name = BasicStaticString{"my.feature"};
  static constexpr auto description = BasicStaticString{"Third-party feature"};
  static constexpr feature::Version version{1, 0, 0};
  static constexpr auto featureKind = feature::FeatureKind::Semantic;
  static constexpr bool enabledByDefault = false;

  static consteval auto dependencies() { return std::array<StringView, 0>{}; }
  static consteval auto optionalDependencies() { return std::array<StringView, 0>{}; }
  static consteval auto conflicts() { return std::array<StringView, 0>{}; }
  static consteval auto implications() { return std::array<StringView, 0>{}; }
  static consteval auto capabilities() { return std::array<feature::Capability, 0>{}; }
  static consteval auto groups() { return std::array<StringView, 0>{}; }
};

inline constexpr MyFeature myFeature{};
static_assert(feature::Feature<MyFeature>);
```

This primitive protocol deliberately stays ordinary C++ so it can bootstrap before the Trait engine exists.

The public convenience concepts are:

```cpp
feature::Feature<T>
feature::FeatureValue<value>
feature::FeatureGroup<T>
feature::FeatureGroupValue<value>
feature::DescriptorOption<T>
```

The type concepts validate protocols; the `*Value` concepts additionally validate structural NTTP values used directly by catalogs and groups.

## Third-party metadata options

The built-in `Descriptor` is also extensible.

An ecosystem option needs only expose an `OptionKind`:

```cpp
struct PackageMetadata final {
  static constexpr auto kind = feature::OptionKind::Custom;
  static constexpr auto package = BasicStaticString{"example"};
};

inline constexpr auto feature =
    feature::define<"feature">(PackageMetadata{});
```

Miracle preserves the option type in `Descriptor::forEachOption`; the resolver simply does not interpret `Custom` metadata.

Descriptor options satisfy `feature::DescriptorOption`. They must be empty and encode metadata in their type/static members, for example:

```cpp
template <BasicStaticString Package>
struct PackageMetadata final {
  static constexpr auto kind = feature::OptionKind::Custom;
  static constexpr auto package = Package;
};

inline constexpr auto value =
    feature::define<"feature">(PackageMetadata<"example">{});
```

This restriction is deliberate. `define(...)` is a function call and standard C++ does not allow an arbitrary function parameter value to become an NTTP in the function's return type. Accepting stateful option objects and then reconstructing `Options{}` would silently lose metadata. Miracle rejects that design instead.

`feature::CustomOptionTag` is provided as a convenience marker for option types that want a reusable built-in `kind` member.

## CMake build bridge

`cmake/Features.cmake` provides the build-system side of the engine.

### Registering a build feature

```cmake
miracle_register_build_feature(
  NAME uuid.v7
  DEFAULT
  DESCRIPTION "UUID version 7 generation"
  DEPENDS uuid
  OPTIONAL_DEPENDS random.hardware
  CONFLICTS uuid.disabled
  IMPLIES uuid
  REQUIRES_CAPABILITIES reflection_core
  GROUPS uuid.all
  SOURCES src/public/UuidV7.ixx
  PUBLIC_LIBRARIES ThirdParty::PublicApi
  PRIVATE_LIBRARIES ThirdParty::Implementation)
```

Supported registration fields are:

```text
NAME
DESCRIPTION
DEFAULT
DEPENDS
OPTIONAL_DEPENDS
CONFLICTS
IMPLIES
REQUIRES_CAPABILITIES
GROUPS
SOURCES
PUBLIC_LIBRARIES
PRIVATE_LIBRARIES
```

The public cache option is derived from the stable feature name:

```text
MIRACLE_FEATURE_UUID_V7
```

Stable names that sanitize to the same CMake identifier are rejected. This prevents names such as `foo-bar` and `foo_bar` from silently sharing a build option.

### Registering a build group

```cmake
miracle_register_feature_group(
  NAME uuid.all
  MEMBERS uuid.v4 uuid.v7)
```

A group can also gain members through each feature's `GROUPS` metadata. Both sources are combined during configuration, so feature/group declaration order does not alter semantics.

Groups expose:

```text
MIRACLE_FEATURE_GROUP_<ID>
```

cache options.

### Build resolution

`miracle_configure_build_features()`:

1. gathers individually enabled feature options;
2. expands enabled groups;
3. follows required dependencies and implications;
4. validates required capabilities;
5. detects complete dependency/implication cycles;
6. checks conflicts over the final closure;
7. sorts enabled names canonically;
8. gathers only enabled heavy module sources and dependency targets;
9. emits generated C++ build-set arguments.

Optional dependencies do not participate in step 3.

The generated values are:

```text
MIRACLE_BUILD_FEATURE_NAMES
MIRACLE_BUILD_FEATURE_ARGUMENTS
MIRACLE_BUILD_FEATURE_SOURCES
MIRACLE_BUILD_FEATURE_PUBLIC_LIBRARIES
MIRACLE_BUILD_FEATURE_PRIVATE_LIBRARIES
```

The root build uses these values to generate `FeatureConfiguration.ixx`, add only selected heavy sources to Miracle's module file set, and link only dependency targets belonging to the resolved build-feature closure. Public/private dependency spelling is preserved so a facility can choose whether the target belongs to Miracle's consumer link interface.

## Build-system portability

CMake is Miracle's current concrete build integration, not the Feature engine's semantic identity.

Another build system can provide the same generated configuration contract:

```text
selected build feature names
+ capability results
+ deterministic build identity
        |
        v
generated Miracle:FeatureConfiguration
        |
        v
typed feature::BuildFeatureSet
```

No downstream C++ facility depends on a CMake variable or macro.

## No hidden work

Feature selection is entirely compile time. `Descriptor`, `Group`, `BuildFeatureSet`, `FeatureSet`, and `Requirement` do not allocate or dispatch at runtime.

Disabled build features do not add their registered `SOURCES` to the Miracle target. A lightweight façade can remain visible for diagnostics without paying for the disabled implementation.

## Compiler-work model

The implementation intentionally avoids repeated type-set reconstruction:

- descriptor relationship arrays are cached once per descriptor specialization;
- one catalog defines one canonical descriptor universe;
- catalog names, feature kinds, default state, capability masks, and graph edges are materialized once per catalog specialization;
- dependency/implication edges are converted from names to canonical indices once;
- resolution uses a flat explicit constexpr stack rather than recursive constant evaluation, so graph depth does not consume compiler constexpr call depth;
- resolved sets are fixed catalog-order bit arrays;
- names are not repeatedly converted to new descriptor types;
- optional metadata is inspected only when requested;
- non-terminating analysis and hard resolution share the same resolver;
- build capability probes are adapted from cached generated facts;
- build feature names and build-universe fingerprints are canonicalized once.

Future Meta/Reflect caching will build on the same principle: sophisticated compile-time behavior is acceptable; redundant compile-time work is not.

## Testing strategy

Feature-engine tests cover both C++ and build-side semantics.

C++ coverage includes:

- descriptor metadata;
- structural NTTP use;
- transitive dependency/implication closure;
- optional dependency non-enabling behavior;
- canonical request-order independence;
- explicit groups and descriptor-side `inGroup` expansion;
- missing build features;
- missing required references;
- missing capabilities;
- dependency cycles with complete cycle text;
- conflicts;
- duplicate catalog names;
- third-party descriptors;
- third-party metadata options;
- structural requirement payloads;
- actual reflection annotation extraction;
- generated capability adaptation;
- disabled-façade compile diagnostics;
- hard compile-fail diagnostics for disabled features, dependency cycles, and conflicts.

CMake script tests independently cover:

- positive canonical closure/source selection;
- groups declared through explicit and feature-side membership;
- dependency cycles;
- conflicts;
- missing dependencies;
- unavailable capabilities;
- sanitized identifier collisions.

The reference C++26 toolchain remains the authoritative module/annotation test lane. Portable standalone validation can exercise the standard compile-time core without changing the production module sources.
