## 1. Intent and boundaries

GitHub's New Issue chooser should route a report or proposal into one of five accurate, concise, structured entry points. Each form should collect *triage-ready* evidence without demanding information the contributor cannot reasonably know. Submissions become ordinary public GitHub Issues, not implicitly accepted design or implementation work.

**Required invariants**

1. Security vulnerabilities are never solicited through public issue forms. Link to `SECURITY.md` instead.
2. An issue is *proposed or reported*, never implicitly approved merely because it was submitted.
3. Neither the form nor a default label may imply that validation, contract acceptance, prioritization, or milestone assignment has occurred.
4. Separate Miracle-library faults from compiler/toolchain defects without preventing uncertain reporters from submitting useful evidence.
5. The form must not require personal contact data, paid services, or a complete independently reproducible test case merely to submit an actionable report.
6. Avoid premature dependencies on G2 Project fields, GitHub Issue Types, labels, or G6 Discussions categories.
7. Existing `SECURITY.md`, `CONTRIBUTING.md`, compiler-support documentation, and locked Miracle contracts remain authoritative for their respective policies.

**Explicitly deferred:** Label taxonomy and automation (G2); PR template (G1.2); Code of Conduct, SUPPORT.md, ACCESSIBILITY.md and detailed confidential reporting channel (G1.3); toolchain-documentation fixes (G1.4); community/operational end-to-end test (G1.5/G6).

## 2. Required file layout

```text
.github/
└── ISSUE_TEMPLATE/
    ├── bug_report.yml
    ├── compiler_issue.yml
    ├── feature_proposal.yml
    ├── architecture_proposal.yml
    ├── infrastructure_issue.yml
    └── config.yml
```

No templates are introduced for public security-vulnerability reports. Documentation defects can be submitted via Bug Report or Infrastructure Request, depending on whether they involve inaccurate product behavior or repository-facing documentation/tooling; the chooser descriptions must make that distinction clear.

## 3. Common schema and UI contract

Each issue form must contain:

- `name`: unique, concise, matching section 4.
- `description`: one sentence clarifying intended use.
- `title`: editable initial title prefix matching section 4.
- `body`: opening `markdown` instructions followed by fields in the listed order.

For every editable field, assign a unique, stable `id` consisting of lowercase letters, digits and hyphens. Use `input` for short single-line answers, `textarea` for narrative/code, and `dropdown` for finite classification. No dropdown receives a preselected default when user judgment is required.

For G1.1, omit top-level `assignees`, `labels`, `projects`, and `type`. They may be introduced only after their target objects, behavior and ownership are established in G2. In particular, labels absent from the repository are not automatically created by issue forms.

Set `validations.required: true` only on the fields marked **Required** below. The UI must explain acceptable uncertainty such as `Unknown`, `Not yet isolated`, or `Not sure` rather than forcing false information. Avoid additional minimum-length constraints, forced acknowledgements, or required upload attachments in the initial version.

Each form starts with a non-submitted `markdown` guidance section:

- Check for an existing report where appropriate.
- Remove credentials, private data and internal paths from shared output.
- Security-sensitive discoveries belong in `SECURITY.md`, not here.
- A submission is not automatic acceptance into the development roadmap.

The actual introduction can be short, with direct hyperlinks to the referenced policies.

### Canonical minimal YAML example (illustrative, not the full implementation)

```yaml
name: Bug Report
description: Report incorrect or regressed behavior in Miracle.
title: "[Bug] "
body:
  - type: markdown
    attributes:
      value: |
        Describe the observed behavior. Do not disclose security vulnerabilities
        or credentials here; see SECURITY.md for private reporting guidance.
  - type: input
    id: affected-revision
    attributes:
      label: Affected revision
      description: Release tag or commit. Enter "Unknown" if necessary.
      placeholder: "v0.5.27, commit SHA, or Unknown"
    validations:
      required: true
  - type: textarea
    id: observed
    attributes:
      label: Observed behavior
      description: What actually happened?
    validations:
      required: true
```

This example communicates the intended schema shape. The author implements all remaining fields according to sections 4–5.

## 4. Exact form definitions

Notation: `R` = GitHub `validations.required: true`; `O` = optional. `input`, `textarea` and `dropdown` refer to native GitHub Issue Form types. All listed IDs are contractual and should remain stable across later wording adjustments.

### 4.1 `bug_report.yml`

Top level:

- `name`: **Bug Report**
- `description`: **Report incorrect or regressed behavior in Miracle.**
- `title`: **`[Bug] `**

| Order | ID | Type | Required | User-visible label | Guidance |
|---:|---|---|:---:|---|---|
| 1 | `affected-revision` | input | R | Affected revision | Tag, branch/commit, or `Unknown` |
| 2 | `affected-area` | dropdown | O | Affected area | Choices below; no default |
| 3 | `observed` | textarea | R | Observed behavior | Actual result; errors or failures |
| 4 | `expected` | textarea | R | Expected behavior | Why behavior appears incorrect |
| 5 | `reproduction` | textarea | R | Reproduction or isolation status | Steps/snippet; if unavailable, explain current blocker |
| 6 | `environment` | textarea | R | Environment | OS, compiler, standard library, CMake configuration, or explicit unknowns |
| 7 | `logs` | textarea | O | Relevant output | Diagnostics/logs; redact sensitive information |
| 8 | `additional-context` | textarea | O | Additional context | Context, links, screenshots/attachments |

`affected-area` options, in order: `Core / Types / Error`, `Diagnostics`, `Ranges / Iter`, `Meta / Reflection`, `Filesystem`, `Build / Features`, `Other`, `Not sure`.

Do not prefill the reproduction field with faux steps that could be submitted as evidence. Use `placeholder` only to explain expectations.

### 4.2 `compiler_issue.yml`

Top level:

- `name`: **Compiler / Toolchain Issue**
- `description`: **Report a C++26 compiler, standard-library, modules or toolchain compatibility problem.**
- `title`: **`[Toolchain] `**

| Order | ID | Type | Required | User-visible label | Guidance |
|---:|---|---|:---:|---|---|
| 1 | `affected-line` | dropdown | R | Affected development line | Choices below; no default |
| 2 | `compiler-identity` | input | R | Compiler and toolchain identity | Exact `clang-cxx26` snapshot/source revision or GCC/libstdc++ version; `Unknown` only if not obtainable |
| 3 | `library-revision` | input | R | Miracle revision | Tag or SHA, or `Unknown` |
| 4 | `component` | dropdown | R | Suspected component | Choices below; include `Not sure` |
| 5 | `observed` | textarea | R | Observed failure | Compiler diagnostics, incorrect behavior, crash, or mismatch |
| 6 | `expected` | textarea | R | Expected behavior | Required by C++26/library contract, with reference if available |
| 7 | `reproduction` | textarea | R | Minimal example or isolation status | Code/commands or explain why not isolated |
| 8 | `compiler-options` | textarea | O | Compiler flags and build configuration | Include `-freflection-latest`, toolchain selection, modules setup if relevant |
| 9 | `logs` | textarea | O | Full diagnostic output | Redacted logs, command output or external repro link |

`affected-line`: `master (reference C++26)`, `gcc (compatibility)`, `Tagged release`, `Not sure`.

`component`: `Clang frontend / reflection`, `libc++ / standard library`, `C++ modules / import std`, `Build / toolchain selection`, `GCC / libstdc++ compatibility`, `Unknown / other`.

The form introduction links to `docs/compiler-support.md` and `docs/reference-toolchain.md`. It explains that some missing standard features are properties of the reference compiler rather than library defects, and that maintainers will triage ownership after submission.

### 4.3 `feature_proposal.yml`

Top level:

- `name`: **Feature Proposal**
- `description`: **Suggest a new Miracle capability or extension to an existing API.**
- `title`: **`[Feature] `**

| Order | ID | Type | Required | User-visible label | Guidance |
|---:|---|---|:---:|---|---|
| 1 | `problem` | textarea | R | Problem and motivation | What should be easier or possible? |
| 2 | `proposed-behavior` | textarea | R | Proposed behavior or API sketch | Consumer-facing code if possible; concrete intended semantics otherwise |
| 3 | `use-case` | textarea | R | Representative use case | Realistic context illustrating the need |
| 4 | `existing-surface` | input | O | Related API or contract | Link to existing docs/contract if known |
| 5 | `alternatives` | textarea | O | Alternatives considered | Existing std/C++26 facilities, workarounds, other libraries |
| 6 | `compatibility` | dropdown | R | Expected compatibility impact | Choices below; no default |
| 7 | `acceptance` | textarea | O | Possible acceptance criteria | Observable outcomes or examples |

`compatibility`: `Additive / likely compatible`, `Potentially breaking`, `Unsure`.

The introduction states that proposals are **not approved design contracts**. The selected API/architecture remains subject to a separate design review and locking process.

### 4.4 `architecture_proposal.yml`

Top level:

- `name`: **Architecture Proposal**
- `description`: **Propose changing a design contract, invariant, ownership model or subsystem boundary.**
- `title`: **`[Design] `**

| Order | ID | Type | Required | User-visible label | Guidance |
|---:|---|---|:---:|---|---|
| 1 | `affected-contract` | input | R | Affected contract or subsystem | Link or name; `New subsystem` if none exists |
| 2 | `motivation` | textarea | R | Problem with the current design | Constraint, cost, defect or new requirement |
| 3 | `proposed-change` | textarea | R | Proposed architecture | Data flow, model, module boundaries or algorithm |
| 4 | `invariants` | textarea | R | Invariants and compatibility | Preserved, changed and potentially violated guarantees |
| 5 | `alternatives` | textarea | R | Alternatives and trade-offs | At least explain which alternatives are known or why undecided |
| 6 | `migration` | textarea | O | Migration or rollout plan | Impact on callers, tests and accepted work |
| 7 | `verification` | textarea | O | How to validate the change | Proposed tests, benchmarks or proofs |

The introduction links to `docs/DEVELOPMENT_PROTOCOL.md` and emphasizes that filing an issue **does not amend** a locked contract. Approval requires an explicit decision and update to the canonical contract (and an ADR if material).

### 4.5 `infrastructure_issue.yml`

Top level:

- `name`: **Infrastructure Request**
- `description`: **Request a change to builds, CI, documentation tooling or repository operations.**
- `title`: **`[Infra] `**

| Order | ID | Type | Required | User-visible label | Guidance |
|---:|---|---|:---:|---|---|
| 1 | `area` | dropdown | R | Infrastructure area | Choices below; no default |
| 2 | `goal` | textarea | R | Goal and current limitation | Why a change is necessary |
| 3 | `affected-config` | input | O | Affected configuration | File, workflow, setting or external integration |
| 4 | `proposed-approach` | textarea | O | Proposed approach | Optional solution; problem reports welcomed |
| 5 | `risks` | textarea | O | Risks and constraints | Security, compatibility, maintenance, billing |
| 6 | `acceptance` | textarea | R | Verification / acceptance evidence | How should we know the change works? |

`area`: `CMake / build system`, `GitHub Actions / CI`, `Compiler provisioning`, `Documentation / publishing`, `Repository configuration`, `Docker / Codespaces`, `Other`.

Avoid collecting API keys, passwords, webhook secrets, internal endpoint credentials or other private administrative information.

## 5. `config.yml` chooser behavior

```yaml
blank_issues_enabled: false
contact_links:
  - name: Report a security vulnerability
    url: https://github.com/spwn02/Miracle/blob/master/SECURITY.md
    about: Read private vulnerability reporting instructions; do not disclose vulnerabilities in public issues.
  - name: Contributing guide
    url: https://github.com/spwn02/Miracle/blob/master/CONTRIBUTING.md
    about: Read contribution requirements and toolchain guidance before submitting a change.
```

Use only the verified repository URLs above. Do not add links to Discussions, SUPPORT.md or a future documentation website until they exist and are maintained. `blank_issues_enabled: false` configures the chooser, but is not a security boundary or a guarantee that maintainers cannot open a blank issue.

## 6. Validation rules and limitations

**GitHub-enforced:** parseable YAML; schema-valid `name`, `description`, `body`; supported field types; distinct field IDs; required-field submission checks; dropdown option selection; configured chooser links.

**Human-enforced at triage:** the correctness of a claimed compiler version, semantic completeness of a reproduction, security triage, duplicates, relationship to an approved design contract, priority, and acceptance status.

Do not claim GitHub can validate arbitrary semantic predicates from these declarative forms. Don't require users to assert successful tests or verify an existing issue without knowing those claims are true. A required field is a completeness signal, not proof.

For `textarea` code/log fields, use GitHub's `render` mode only when the benefit of fenced code outweighs the loss of normal attachment and Markdown editing in that field. Use an ordinary textarea for freeform reproduction and extra context.

## 7. Implementation sequence (author-owned)

1. Add the six YAML files under `.github/ISSUE_TEMPLATE/` without modifying any product source files.
2. Keep each form's top-level strings, stable field IDs, input types, requiredness and dropdown options consistent with this contract.
3. Run a local YAML syntax check; ideally validate against a GitHub Issue Form-compatible schema.
4. Push to a review branch or author-approved integration path. Open `https://github.com/spwn02/Miracle/issues/new/choose` to validate actual rendering and navigation.
5. Check required vs optional submission behavior and verify security routing. Avoid publishing real credentials or vulnerability details during testing.
6. Obtain milestone review and record implementation/verification evidence in `docs/infrastructure/G1-PROGRESS.md` (create as part of G1 organization if desired).

## 8. Acceptance matrix

| Test | Evidence | Required result |
|---|---|---|
| Form discovery | New Issue chooser inspected | Exactly five named forms and required contact links appear |
| Schema validity | YAML parsing and actual GitHub render | No validation/render errors |
| Required fields | Each form tried without required input | Submission blocked for missing required fields |
| Unknown values | Submit-preview interaction with incomplete environment data | Legitimate `Unknown` / `Not sure` pathway exists |
| Security redirect | Open security contact link | Resolved route goes to `SECURITY.md`, not a public issue form |
| No premature metadata | Review template sources and resulting chooser | No unapproved labels, assignees, issue types or Project bindings |
| Architecture authority | Architecture and feature introductions inspected | No proposal described as approved contract |
| Revisions and routes | Links to compiler/protocol/contributing docs inspected | All resolve to current repository files |
| Git diff scope | `git diff --check`; changed-file inventory | Only G1.1 forms and explicitly required G1 documentation/ledger changes |
| Review | Contract-aware milestone review | All blockers resolved; author accepts milestone |

No need to create permanent fake public issues merely to test chooser rendering. If a genuine test issue is created, clearly mark it as a test and close it with an explanation; do not fabricate completed feature history.

## 9. Follow-up boundaries

G1.2 specifies the pull request template. G1.3 specifies conduct, support and accessibility policy. G1.4 corrects toolchain documentation and strengthens contributor onboarding. G1.5 verifies community file discovery and full contribution intake. G2 defines authoritative Project fields, labels, and issue routing automation.
